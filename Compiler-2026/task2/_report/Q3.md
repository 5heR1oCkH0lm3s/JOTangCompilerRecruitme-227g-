# TASK2 Q3

>`ir/opt`封装了各类 IR 变换优化 Pass。在`main.cpp`中，**PassBuilder** 会将这些优化按顺序组织成 **Pipeline** ，对生成的 IR 进行优化。

## NewPassManager

>ps.本文以 Transform Pass 的完整生命周期为主线回答问题。"TransformPass 调用的整个流程"即主线本身，其余六个概念（Pass Pipeline 构建、CRTP、类型擦除、PassID、AnalysisPass、自动失效）在流程走到对应位置时单独引出解释。

---

### 一、初始化

整个中端优化的架构与流程从初始化阶段开始，系统首先利用 **CRTP（奇异递归模板模式）** 让所有分析与变换功能在编译期自动继承基类，从而为每个 Pass 生成一个基于**空类 PassID** 的全局唯一物理内存地址作为身份令牌。紧接着，系统实例化了两个核心枢纽：分析管理器（AM，如`FAM/MAM`），以及变换管理器（PM，如`FPM/MPM`）。随后 `PassBuilder` 将 6 项 `Pass` **类型擦除**后依次 `.addPass` 进 `FPM`。

#### 1.1 CRTP 设计模式

* **CRTP（Curiously Recurring Template Pattern，奇异递归模板模式）** 是指派生类将自身作为模板参数传递给基类,从而在编译期实现静态多态的设计模式。

* 基类定义`template <typename DerivedT> struct AnalysisDescriptor`并通过`return &DerivedT::Key`预设逻辑，子类只需以`class PassA : public AnalysisDescriptor<PassA>`继承并声明`static PassID Key`，编译器就会自动为其生成精准返回自身变量地址的 ID() 方法。

* CRTP 既免除了各派生类重复编写相同接口的冗余工作，又彻底消除了传统虚函数的运行时查表开销，以"零性能代价"实现了代码复用。

#### 1.2 AnalysisPass 的注册

* `PassBuilder::registerFunctionAnalyses`通过`X-Macro`展开 `FunctionAnalysisPass.def`中的分析清单，对每一项调用`AnalysisPassManager::registerPass`。`registerPass`用`decltype`(工厂的返回值) 推导分析类型，以`PassT::ID()`为键将该类型的工厂包装成类型擦除对象存入`AnalysisPasses`；注册的是"如何计算"而非计算结果，因此是无副作用的登记动作。

* 值得注意的是:
  1. **AnalysisPass是"注册"**：`registerPass` 只登记"如何计算"，把对应类型的工厂包装成类型擦除对象存入注册表 `AnalysisPasses`，此时并不进行任何实际计算；注册是无副作用的登记动作，真正的计算推迟到有 Pass 索要时才发生。
  2. **TransformPass是"添加"**：`addPass` 把具体的、已经构造好的 TransformPass 实例按顺序装进 `FPM` 的内部数组，等待流水线启动后按序执行。
  > 前者按需触发（惰性求值），后者按序执行。

### 二、组装

为了组装这条流水线，系统应用 **类型擦除（Type Erasure）** 技术，将不同类型的具体`Transform Pass`抹去差异，包装成统一的接口黑盒，按顺序装填进`FPM`中。随后，为了让模块级的`MPM`能够跨层级调度这些函数级优化，系统使用**转接桥** `ModuleFunctionBridge`将`FPM`与配套的`FAM`打包在一起，再次进行**类型擦除**，将其伪装成一个普通的模块级 Pass 挂载到`MPM`之中。

#### 2.1 类型擦除

* **类型擦除（Type Erasure）** 是一种结合 C++ 模板与多态的技术，通过抽象基类和模板包装器在运行时隐藏对象的具体类型并对外提供统一接口，降低了代码耦合。

* 该项目在`NewPassManager.hpp`中通过纯虚基类`PassInterface`定义统一执行接口`virtual PassResult run(IR, AM) = 0`，把 Pass 具体类型这一信息在编译期抹掉，只保留一个统一的`run`接口，从而让类型完全不同的 Pass 能被同一个 `PassManager` 存放和驱动，并利用模板类`PassWrapper`动态包装任意具备相应方法的具体 Pass 实例。

* `PassManager::run`只需对 `PassInterface`逐项调用 `Pass->run(IR, AM)`，无需知道具体 Pass 类型。即使新增一个 Pass 只需写类 + 一行 `addPass`，无需修改`PassManager`。

> **转接桥包装**：6 项 Transform Pass 装填进 `FPM` 后，面临一个层级问题：最外层的调度对象是模块，而 `FPM` 是函数级的。于是 `PassBuilder` 用 `createModuleFunctionBridge` 把 `FPM` 类型擦除后包成转接桥（桥内持有 `FAM` 的引用），并作为唯一一项 `.addPass` 进 `MPM`。`-O0` 时直接返回空的 `MPM`。

#### 2.2 Pass Pipeline

* 本项目中端优化执行了以下TransformPass:
  1. `PromotePass`: 把`alloca/load/store`提升为 SSA 的`PHI`
  2. `LoopSimplifyPass`：把每个循环规范化为唯一`preheader`、唯一`latch`与专用出口
  3. `LCSSAPass`：循环内定义、循环外使用的值，统一收进出口`LCSSA PHI`
  4. `LocalGVNPass`:块内值编号，消除单个基本块内的重复整数纯计算
  5. `LICMPass`：把循环不变量外提到`preheader`
  6. `LocalGVNPass`：再次消除`LICM`把不同循环块的计算集中到同一`preheader`后新产生的块内冗余。
  >`Mem2Reg`让`IR`进入`SSA`形式，`LoopSimplify`与`LCSSA`提供规范化的循环结构，这三者是`GVN`与`LICM`的前置条件；`LICM`外提产生的冗余由末尾的`GVN`收尾。

### 三、执行

`main`调用`MPM.run(*ModuleIR, MAM)`，把初始 IR 作为`Module`交给`MPM`，并在`MAM`管理下执行。`MPM`逐项调用 Pass，唯一一项就是**转接桥**，取出后调用它的`.run`。桥遍历`Module`里的每个`Function`，对每个函数调用一次`Pass->run`,这里的 Pass 指的是被包装过的整条`FPM`，于是直接进入`FunctionPassManager::run`，由它再逐个执行那 6 个具体 Pass。

在具体的 TransformPass 修改 IR 前，它需要获取支配树和循环信息，于是向`FAM`索要数据。其中的数据传递依赖于`PassID`。

#### 3.1 PassID：空类

* `PassID`是一个采用`alignas(8)`内存对齐的空结构体，其核心设计思想是"以物理地址的绝对唯一性作为身份标识"。项目中每个具体的分析类均声明了一个 `static PassID Key`静态成员，并通过 CRTP 基类`AnalysisDescriptor<DerivedT>::ID()`返回该成员的内存地址，将其作为该分析类型的全局唯一标识。由于静态成员在程序生命周期内地址固定且不同类之间必然互异，该指针被直接用作底层分析与结果缓存的检索。

* `FAM`将`PassID`提供的内存地址，与当前正在处理的 IR 单元的物理内存地址组合在一起，构成了一个联合键`CacheKey = std::pair<PassID*, IRUnitT*>`。整个缓存字典`ResultCache`的存取、寻址以及依赖图的构建，完全是围绕这个由物理指针构成的联合键来高效运转的。

#### 3.2 AnalysisPass 的调用

* `getResult<AnalysisT>(IR)`以`(AnalysisT::ID(), &IR)` 为键查询`ResultCache`，命中直接返回；未命中则以`RAII`压入`ActiveAnalysisStack`、调用类型擦除后的分析并缓存结果。构造过程中若发生嵌套的`getResult`，会把"当前分析依赖被查询分析"记录进 `AnalysisDependencies` / `ReverseAnalysisDependencies`，供失效时做传递闭包。项目中的实例是 `LoopAnalysis::run`内部调用`getResult<DominantAnalysis>`，从而形成"LoopInfo 依赖支配树"的边。

* **惰性求值**：`FAM`接拿着目标分析类的`PassID`地址去缓存字典里查表，若有缓存则直接返回，若无缓存才临时唤醒对应的 AnalysisPass 进行现场计算、记录进依赖图并存入缓存。

---

### 四、收尾

内层每跑完一个 Pass 会返回`PassResult`，`FPM`会有两步收尾动作：维护缓存与合并改动。`PassManager::run`会调用`AM.invalidate(IR, Current)`清理缓存（即**自动失效机制**），同时把保留状态`merge`进`PA`,并记录`Changed`。

#### 4.1 自动失效

* `PassResult`包含两项：`IRChanged`（是否修改 IR）与 `PreservationStatus`（仍有效的分析集合）。其中`PreservationStatus` 由全保留开关`PreservedAll`、保留白名单`PreservedIDs`、失效黑名单`AbandonedIDs`三部分组成。Pass 通过`keep<T>()`/`discard<T>()`写入这两个集合。查询统一走 `isKept`：黑名单优先，否则看全保留开关或白名单。

* `FAM`在遍历缓存列表时，完全不需要拆开**类型擦除**的包装，而是直接提取每个缓存条目的 **PassID** 物理地址。流程如下：
  1. `IRChanged` 为假直接返回
  2. 遍历分析缓存筛选失效项：不属于本次修改的 IR 单元则跳过，`PA.isKept(PassID)` 为假则失效。若该分析实现了 `invalidate(IR, PA)` 钩子，则优先采用其结论。
  3. 沿反向依赖图做传递闭包，某个分析失效时所有依赖它构造出的分析一并失效
  4. 删除失效条目对应的缓存结果，并同步清除依赖图中的相关边
  5. 若本次失效未由桥接层处理，则通过 `IRMutationCallback` 通知外层管理器清理上层缓存

遍历完整个`Module`后,`PA`记录的是逐函数合并出的有效分析集合，`Changed`记录整个模块是否被改过。转接桥把这个结果向上返回给`MPM`，以决定是否触发外层模块级的缓存清理：如果`Changed=True`就标记`PA`并返回`changed`,避免`MAM`回调`FAM.clear()`重复清空。反之则直接返回`unchanged`。
